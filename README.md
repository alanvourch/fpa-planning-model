# Northlight: a driver-based plan that decides headcount, cloud and product spend

A planning and scenario model for a fictional Series C software company, built to
answer one executive question: how should the CFO and the head of engineering
allocate headcount, cloud and vendor spend and product investment over the next
18 months while protecting gross margin and cash runway?

The model answers it. It evaluates three hiring plans crossed with two cloud
purchasing choices under base, upside and downside scenarios, applies two
guardrails (downside runway and a gross margin floor), and recommends the option
that grows ARR most among those that pass. The recommendation, the numbers behind
it, a one-page CFO memo, a five-slide board pack and an auditable Excel workbook
are all generated by one command. No language model is used anywhere; every
number is produced by ordinary finance arithmetic that the tests check.

**Rather see it than read it?** The two-minute version, with the charts and the
downloadable memo, board pack and workbook:
**[the live case study](https://alanvourch.com/fpa-planning-model/)** (built from
`site/index.html`). A companion project,
[the automated monthly close](https://github.com/alanvourch/fpa-project), covers
the backward-looking half of the FP&A loop; this one is the forward-looking half.

## The conclusion

Northlight is at about USD 24M of ARR, growing about 40% a year, with about USD
25M of cash and a monthly net burn near USD 0.8M. Gross margin has slipped below
budget because customers of the data-heavy Insights add-on consume about a third
more compute than planned.

The model recommends the phased hiring plan (22 hires from October 2026 to May
2027, 14 of them in R&D) together with a one-year cloud commitment. The
front-loaded plan (31 hires plus contractors) buys under USD 2M of extra ARR by
February 2028 and breaks the 18-month downside runway guardrail. Running cloud on
demand fails the gross margin floor in every hiring plan. Holding hiring keeps
more cash but ends well below the recommended plan in ARR. The exact figures are
in `output/decision.json`, `output/option_verdict.csv` and the memo.

## What the model contains

- **A synthetic dataset from a fixed seed**: 24 months of actuals (September 2024
  to August 2026) with a real roster (start and end dates, backfills), realized
  drivers, and the FY2026 budget as locked in December 2025. Six deviations from
  budget are planted and documented in `model/dataset.py`.
- **A workforce plan by role and location** (Montréal, Paris, Austin): salary,
  bonus, employer taxes derived from published 2026 rate tables, benefits, merit,
  recruiting cost, equipment capex, ramp for sales and customer success, and a
  vacancy allowance for attrition.
- **Revenue from drivers, not growth rates**: new customers from ramped sales
  capacity times productivity times seasonality; churn and expansion from gross
  and net retention; a January price step; an add-on modelled as attach rate
  times usage.
- **Cloud and vendor spend on usage drivers**: compute units per customer by
  product, unit price with drift, a commitment rule (discounted committed units,
  overage at list), third-party fees and payment processing as shares of revenue,
  tooling and software seats per head, rent per head by location.
- **P&L by function and by product line** (to gross profit), and cash with
  receivables, deferred revenue and financing. Runway is cash over trailing burn.
- **Base, upside and downside** from one assumption table with three columns.
  Nothing scenario-specific is typed into the outputs.
- **A monthly actual-versus-plan bridge** that splits every P&L line into driver
  components (volume and price, headcount and rate, usage and unit cost) whose
  sum equals the EBITDA variance to the cent, with a dual materiality test.
- **Assumption versioning**: the FY2026 budget snapshot, the current file, and a
  change log recording each change, when, by whom and why. A test replays the log
  onto the snapshot and requires the result to equal the current file. Values are
  changed through `tools/change_assumption.py`, which writes the log entry.
- **An Excel export** (`output/northlight_planning_model.xlsx`) in which leaf
  values come from the model and every subtotal, margin, cloud rule, cash
  roll-forward and check is an Excel formula. A Checks sheet recomputes each
  subtotal against the model value.
- **A CFO memo and a board pack** rendered from a facts dictionary that reads
  only model outputs, and a **single self-contained web page** with inline SVG
  charts, built the same way.

## How it is checked

`tests/` holds 43 tests, run with `pytest -q`:

- `test_reconciliation.py`: ARR roll-forward, P&L subtotals, product P&L,
  payroll to the workforce table, the cloud rule, the cash roll-forward and
  determinism, for all 18 scenario runs plus actuals and budget; and a check that
  outputs move when a driver moves.
- `test_workforce.py`: a hire costs exactly its loaded salary from its start
  month, merit applies every January after the start, an end date stops cost, an
  account executive adds customers only after ramp, and one extra engineer moves
  EBITDA and cash by exactly the expected amount.
- `test_bridge.py`: components tie to each line and to EBITDA every month, the
  materiality rule matches the assumptions, and the six planted deviations are
  recovered with the right sign in the right component.
- `test_assumptions.py`: every driver carries a source label, benchmark rows
  name a source that was read, snapshot plus change log equals the current file.
- `test_excel.py`: workbook values equal the Python output; and, where Microsoft
  Excel is installed, Excel recalculates the workbook and every formula result is
  compared to the model value.
- `test_documents.py`: every number in the memo and on the web page traces to a
  model output; page counts; no external assets; no hype words or em dashes.
- `test_adversarial.py`: shifting every planned hire by one month changes people
  cost by exactly one seat-month per seat; the renderers contain no typed
  figures; and the recommendation changes when the guardrail changes.

`DECISIONS.md` records every modelling and design choice, including the ones
rejected and what the adversarial tests caught.

## Where the numbers come from

Every driver in `assumptions/assumptions.csv` carries one of three labels:

- **benchmark**: a figure from a published survey that was read for this
  project (SaaS Capital's 2025 retention and 2026 spending and growth
  benchmarks; Benchmarkit's 2025 performance metrics), quoted in the source
  column;
- **derived**: computed from a published rate table (Québec 2026 employer
  contributions, the French employer share per PwC's tax summary, US employer
  payroll taxes per the IRS), with the derivation in the source column;
- **judgment**: the author's call, marked as such, with no source claimed.

Most drivers are judgment calls, on purpose: the point is to show the
machinery and label the inputs honestly, not to pretend a synthetic company has
a survey behind every number.

## Known limitations

- The actuals are generated by the same engine from realized drivers, so the
  bridge reconciles exactly by construction. A real ledger needs a
  reconciliation tolerance and an unallocated line.
- No interest, income tax, depreciation, capitalized development or foreign
  exchange. EBITDA is the operating line; salaries are stated in USD.
- Plan headcount carries attrition as an expected vacancy allowance, so plan
  FTE is fractional. Actuals carry real leavers.
- Marketing programme spend scales with the new-customer target rather than
  driving it.
- Customer success is the only function hired automatically from a driver;
  every other hire is a plan line.
- The option set is small by design (three hiring plans, two cloud choices).
  The engine can run any hiring plan added to `assumptions/hiring_plans.csv`
  and any option added to `assumptions/options.csv`.

## Run it yourself

Python 3.12 and git. Run everything from the repository root.

**Windows (PowerShell):**

```powershell
git clone https://github.com/alanvourch/fpa-planning-model.git
cd fpa-planning-model
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python.exe run_model.py
.venv\Scripts\python.exe -m pytest -q
```

**macOS / Linux:**

```bash
git clone https://github.com/alanvourch/fpa-planning-model.git
cd fpa-planning-model
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python run_model.py
.venv/bin/python -m pytest -q
```

`run_model.py` regenerates `data/` (actuals, budget, roster, drivers),
`output/` (bridge, option grid, the 18 scenario runs, the Excel workbook, the
memo, the board pack) and `site/index.html`. The run is deterministic: two runs
give identical files apart from the date in the memo.

To change an assumption and keep the audit trail:

```powershell
.venv\Scripts\python.exe tools\change_assumption.py --id nrr_annual --scenario base --value 1.04 --version 1.4 --by "Your name" --reason "Q3 churn review"
```

## Tech stack

Python 3.12, pandas, numpy, openpyxl (Excel export), matplotlib (board pack
charts), fpdf2 (memo PDF), pytest. Nothing else: no language model, no
dashboard tool, no JavaScript on the page.
